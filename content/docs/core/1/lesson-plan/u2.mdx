## MODULE 1: Selection & Conditional Branching (if, else, elif)

### **Lesson Objective**
Construct multi-way decision trees in Python using proper block indentation, evaluate compound conditional expressions utilizing logical operator precedence and short-circuit mechanics, and distinguish between value equality (==) and reference identity (is) comparisons [B1 Ch. 7, B5 Ch. 6].

### **Core Concepts**
* **Block Indentation (Suites):** Explain how Python uses whitespace indentation (standard 4 spaces) instead of C's curly braces (`{}`) to define blocks of code (called "suites") [B5 Page 119]. A header statement (like `if`, `while`, or `def`) must terminate with a colon (`:`) [B5 Page 119].
* **Conditional Branching:** Trace the evaluation sequence of simple `if` [B1 Page 217, B5 Page 121], two-way `if-else` [B1 Page 218, B5 Page 121], and multi-way `if-elif-else` chains [B1 Page 222, B5 Page 122]. Emphasize that once a condition in an `if-elif` chain evaluates to True, remaining conditions are bypassed completely.
* **Logical Precedence & Short-Circuiting:** Explain logical operators (`and`, `or`, `not`) [B1 Page 256, B5 Page 81]. Python evaluates logical expressions left-to-right and employs short-circuit evaluation:
  * `A or B`: If `A` is truthy, `B` is never evaluated; the expression immediately returns the value of `A` [B1 Page 267].
  * `A and B`: If `A` is falsy, `B` is never evaluated; the expression immediately returns the value of `A` [B1 Page 267].
* **Equality vs. Identity:** Value comparison (`==`) evaluates whether two objects contain the same data [B5 Page 85]. Identity comparison (`is`) checks whether both variables point to the exact same physical memory address on the heap [B5 Page 85].

## MODULE 2: Iterative Control Structures: Indefinite Loops (while Loops)

### **Lesson Objective**
Implement indefinite iteration using while loops, design sentinel-controlled and interactive input loops, incorporate priming reads to prevent processing the sentinel value, and establish termination boundaries to avoid infinite loop states [B1 Ch. 8, B5 Ch. 6].

### **Core Concepts**
* **Indefinite Iteration:** Contrast definite loops (where the number of passes is known in advance) with indefinite loops (which run as long as an expression condition remains True) [B1 Page 245, B5 Page 124].
* **Execution Lifecycle:** The condition expression is evaluated before entering the loop body (a pre-test loop) [B1 Page 245, B5 Page 124]. If it evaluates to False on the first check, the loop body is bypassed entirely [B1 Page 245, B5 Page 124].
* **The Priming Read Pattern:** When building a sentinel loop (a loop designed to process a continuous stream of user inputs until a special "sentinel" value like -1 or "quit" is encountered), a programmer must utilize a priming read before the loop header [B1 Page 250]:
  * Read first value (Priming Read)
  * While value is not Sentinel:
    * Process value
    * Read next value (Loop Update Read)
  * This sequence ensures that the sentinel value itself is never erroneously sent through the processing suite [B1 Page 250].

## MODULE 4: Control Flow Jumps & Advanced Loops (break, continue, pass, else)

### **Lesson Objective**
Alter loop execution paths dynamically using break and continue jump statements, deploy the pass statement as a syntactic placeholder, and utilize the unique Python loop else suite to eliminate redundant boolean flags [B5 Ch. 6, B3 Ch. 4].

### **Core Concepts**
* **The break Statement:** Immediately terminates the execution of the nearest enclosing loop, jumping to the first statement following the loop block [B5 Page 138, B1 Page 263].
* **The continue Statement:** Aborts the remainder of the current loop iteration, transferring control immediately back to the loop header for the next validation check [B5 Page 138].
* **The pass Statement:** Acts as a syntactic null statement. Since Python's compiler requires block bodies to contain at least one instruction, pass is utilized to write empty skeleton classes, functions, or exception catch blocks without raising a compilation error [B5 Page 139].
* **The Loop else Suite:** A unique Python control flow structure. An else block associated with a for or while loop executes only if the loop completes its iterations naturally [B5 Page 172, B3 Page 172]. If the loop is terminated prematurely by a break statement, the else block is completely bypassed [B5 Page 172]. This allows developers to write clean search patterns without introducing temporary "found" boolean flags [B3 Page 172].

## MODULE 5: Functions, Parameters, and Scope (LEGB Rule)

### **Lesson Objective**
Define and invoke functions utilizing explicit parameter lists and return vectors, trace the execution of Python’s Pass-by-Object-Reference memory model across mutable and immutable datatypes, and apply the LEGB rule to resolve variable scope boundaries [B1 Ch. 6, B5 Ch. 9].

### **Core Concepts**
* **Procedural vs. Functional Decomposition:** Explain why programmers divide complex code blocks into modular, cooperative functions to eliminate code duplication and isolate logic [B1 Page 177, B5 Page 237].
* **Parameter Passing — Pass-by-Object-Reference:** Contrast Python with C (pass-by-value/pass-by-pointer) [B5 Page 248]. In Python, variable names are tags bound to heap objects [B5 Page 49]. When calling a function, a copy of the reference is passed to the formal parameter:
  * **Immutable arguments (int, float, str, tuple):** Since the underlying object cannot be altered in-place, reassigning the parameter inside the function merely binds the local name tag to a new object. The original caller variable is unaffected [B5 Page 250, B1 Page 195].
  * **Mutable arguments (list, dict, set):** Modifying the parameter's internal state in-place (e.g., `list.append()`) directly modifies the shared object. These changes are visible to the caller [B5 Page 251, B1 Page 193].
  * **Safety Trap:** Creating an entirely new object inside the function (e.g., `lst = [10, 11, 12]`) rebinds the local name tag to a new location. It does not overwrite the caller's list [B5 Page 252].
* **Scope Resolution (The LEGB Rule):** Namespaces are resolved from inside out across four distinct hierarchical boundaries [B5 Page 258]:
  * **Local:** Defined inside the current active function block.
  * **Enclosing:** Defined inside a nested outer function envelope.
  * **Global:** Defined at the module's top-level script layer.
  * **Built-in:** Python's system-predefined keywords and built-in routines.
* **The global Keyword:** Explicitly overrides local shadowing, instructing the interpreter to compile reassignments directly against the global module-level variable namespace [B5 Page 258].

## MODULE 6: Dynamic Parameter Architectures & Lambda Expressions

### **Lesson Objective**
Construct functions that accept positional, keyword, default, and variable-length arguments (*args/**kwargs), and build lightweight, anonymous lambda expressions integrated within functional mappings (map/filter) [B5 Ch. 9].

### **Core Concepts**
* **Argument Classification:**
  * **Positional Arguments:** Arguments passed to a function must match the exact sequence order of the formal parameters in the definition [B5 Page 253].
  * **Keyword Arguments:** Arguments specified explicitly by name during invocation, enabling parameter values to be passed in any sequence [B5 Page 254].
  * **Default Arguments:** Assigns default fallback values to formal parameters if left unspecified during call invocation. Non-default arguments cannot follow default arguments in definitions [B5 Page 255].
* **Variable-Length Argument Architectures:**
  * `*args` (Positional Packing): Instructs the interpreter to pack any additional positional arguments passed during the call into a single, iterable tuple parameter named `args` [B5 Page 256].
  * `**kwargs` (Keyword Packing): Instructs the interpreter to pack any additional keyword arguments passed during the call into a single, searchable dictionary parameter named `kwargs` [B5 Page 257].
* **Anonymous Lambda Expressions:**
  * Syntactically represented as: `lambda arguments: single_expression` [B5 Page 265].
  * Lambdas do not use a `return` keyword (the evaluated expression is returned implicitly) and are restricted to a single logical line [B5 Page 265]. They are best utilized as inline operations inside functional sequence processors like `map()` and `filter()` [B5 Page 266–267].

## MODULE 7: Recursive Problem Solving & Stack Frame Analysis

### **Lesson Objective**
Explain the mathematical principles of recursive decomposition, identify the essential base case and recursive step requirements to prevent infinite recursion runtime stack crashes, and map the stack push/pop lifecycle of a recursive function call [B1 Ch. 13, B5 Ch. 9].

### **Core Concepts**
* **The Divide-and-Conquer Methodology:** Recursion is a programming technique where a function solves a complex problem by calling itself to solve smaller, identical instances of the same problem [B1 Page 465, B5 Page 262].
* **The Two Laws of Recursion:**
  * **The Base Case:** A terminal boundary condition that can be evaluated and resolved directly without requiring further self-calls [B1 Page 467, B5 Page 262].
  * **The Recursive Step (Reduction):** The self-referential call must operate on a progressively smaller version of the problem, ensuring that the execution chain always converges toward a base case [B1 Page 467, B5 Page 262].
* **Recursive Stack Frame Lifecycles:**
  * Each recursive call suspends the current parent execution scope and pushes a new activation record (stack frame) onto the system call stack [B1 Page 468, B5 Page 216].
  * The system stack stores the local variable namespaces and current return addresses.
  * If the execution loop fails to reach a base case, it consumes all available system memory slots, resulting in a `RecursionError` (Maximum Recursion Depth Exceeded / Stack Overflow) [B5 Page 216].
* **The Towers of Hanoi:** A classic recursive divide-and-conquer problem where moving $n$ disks from Post A to Post C using spare Post B requires recursively moving a sub-tower of size $n-1$ [B5 Page 264, B3 Page 239].

    # 1. Recursive Factorial with Call Stack Trace Logging
    def trace_factorial(n, depth=0):
        indent = "  " * depth
        print(f"{indent}--> PUSH: Entering trace_factorial(n={n})")

        if n == 0 or n == 1:
            print(f"{indent}<-- POP: BASE CASE reached. Returning 1")
            return 1
        else:
            sub_problem = trace_factorial(n - 1, depth + 1)
            result = n * sub_problem
            print(f"{indent}<-- POP: Multiplying {n} * {sub_problem}. Returning {result}")
            return result

    trace_factorial(4)
    print()

    # 2. Towers of Hanoi Recursive Solver
    # Moves n disks from source pole to destination pole using intermediate pole
    def solve_hanoi(n, source, destination, intermediate):
        if n == 1:
            print(f"Move disk 1 from pole {source} to pole {destination}")
            return

        # Step A: Move n-1 disks from source to intermediate using destination
        solve_hanoi(n - 1, source, intermediate, destination)

        # Step B: Move the remaining largest disk from source to destination
        print(f"Move disk {n} from pole {source} to pole {destination}")

        # Step C: Move n-1 disks from intermediate to destination using source
        solve_hanoi(n - 1, intermediate, destination, source)

    print("Solving Towers of Hanoi for 3 disks:")
    solve_hanoi(3, "A", "C", "B")
